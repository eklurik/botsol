# Правила бота: что делает каждое и как читать граф

Файл `01_Правила_бота_граф.jdm.json` — набор правил в формате **JDM** (GoRules Zen). Открывается
в любом редакторе JSON, но по-человечески читается в редакторе таблиц решений
([gorules/jdm-editor](https://github.com/gorules/jdm-editor), MIT) или движком
[`@gorules/zen-engine`](https://www.npmjs.com/package/@gorules/zen-engine).

## Как устроен граф

```
обращение → 0a. сигналы из тикета → 0b. производные сигналы
          → 1. ЛЕСТНИЦА ПРИОРИТЕТОВ (18 условий подряд, первое совпавшее выигрывает)
          → узел конкретного правила → решение
```

Ключевое для понимания: **порядок условий в лестнице = приоритет правил**. Работает политика
«первое совпадение» (`hitPolicy: first`), поэтому если два правила подходят под ситуацию,
сработает то, что выше. Именно этот порядок раньше был размазан по сотням строк условий в коде —
здесь он виден одним экраном и редактируется перетаскиванием.

Там, где правило само по себе ветвится (R5, R11, R14, R2), внутри стоит мини-таблица решений на
2–3 строки: колонки — условия, строки — варианты, последняя строка обычно «по умолчанию».

## Правила, по порядку приоритета

| № | Правило | Когда срабатывает | Что делает |
|---|---|---|---|
| 1 | **R1** | Запрос на удаление аккаунта | Шаблонный ответ (14 дней), закрывает тикет |
| 2 | **R7** | Вывод средств с баланса на карту | Шаблон + флаг оператору (сам вывод делает бэк-офис) |
| 3 | **R10** | Воздушная тревога + запрещённая зона + спор о штрафе | Снять штраф (клиент не мог безопасно переставить ТС); работает A/B |
| 4 | **R5** | «Не могу завершить» + ровно одна активная поездка + зона НЕ запрещена | Бот завершает поездку сам |
| 5 | **R12** | Короткая отменённая поездка в чёрной зоне после успешного старта | Объяснение блокировки зоной |
| 6 | **R6** | Точный `unlock_failed` + жалоба «не разблокировался» | Объяснение, без выводов о деньгах |
| 7 | **R3** | Датчики: не двигался И мотор не включался | Поездки фактически не было → возврат |
| 8 | **R4** | `unlock_failed` + ошибка IoT | Заявка технику + отдельная проверка платежа |
| 9 | **R8** | Жалоба «сломан» + подтверждённая ошибка IoT | Авто-заявка технику + рекомендация перерасчёта |
| 10 | **R11** | Жалоба на неисправность БЕЗ подтверждения датчиками | Ветвится: 0 ₴ и первое обращение → доверяем; risk-клиент или ≥2 обращений за 30 дней → оператор; есть списание → перерасчёт вручную |
| 11 | **R-F4** | Жалоба «сломан», но IoT в норме (мотор работал, было движение) | Просим детали/фото, автоматически НЕ компенсируем |
| 12 | **R14** | Списание > 0 в чёрной/красной зоне + спор | Ветвится: на границе зоны (`borderline`) → вероятная ошибка GPS, вернём; добросовестный клиент → «передаю на проверку»; risk или ≥2 возвратов за 30 дней → только вручную |
| 13 | **R9** | Финиш в сервисной зоне + спор о штрафе | Перепроверить живой GPS, затем подтвердить перерасчёт |
| 14 | **R2** | Платная (синяя) зона + спор о доплате 100 ₴ | Ветвится по GPS: уверенно в зоне → объяснить; на границе или ненадёжный GPS → вернуть |
| 15 | **GR1** | Активная аренда + ТС в запрещённой зоне + «не едет/застрял» | Предложение grace-разблокировки на 3 минуты с контролем направления |
| 16 | **RN2** | Активная поездка + ТС в запрещённой зоне (без grace) | «Верните в разрешённую зону и завершите там» |
| 17 | **RN1** | Абонемент на разблокировку + нулевой баланс | Объяснить: нужно пополнение, это не возврат |
| 18 | **R13** | Новый пользователь + нулевой баланс, без жалобы | Тёплая пошаговая инструкция старта |

Если не совпало ни одно условие — правило не срабатывает, ответ формирует языковая модель по
промпту (в этот пакет промпт не входит).

## Важные детали, которые видно в графе

**Тексты отделены от логики.** Правило возвращает не текст, а ключ (`replyKey`, `opNoteKey`);
сами формулировки живут в отдельном файле канонов. Смысл: оператор правит текст ответа, не рискуя
задеть условие, и наоборот.

**Гарды важнее самих правил.** Много условий в лестнице — это защиты, добытые из реальных
инцидентов: R14 не срабатывает при активной аренде (иначе бот обещает перерасчёт не той поездки);
RN2 не срабатывает во время тревоги (иначе бот советует ехать под сиреной); R12 требует точной
комбинации событий, а не просто «поломки». Ломать их правкой — самый вероятный способ навредить.

**Анти-абьюз в денежных правилах.** R11 и R14 считают, сколько раз этот клиент уже получал
доверие или возврат за 30 дней, и переключают ветку на ручную проверку.

## Как прогнать правила локально

```bash
npm i @gorules/zen-engine
```

```js
import { ZenEngine } from '@gorules/zen-engine';
import { readFileSync } from 'node:fs';

const graph = JSON.parse(readFileSync('01_Правила_бота_граф.jdm.json', 'utf8'));
const decision = new ZenEngine().createDecision(graph);

// вход берётся из файла переписок: signals.flags + signals.snapshot + intents + live + history
const { result } = await decision.evaluate({
  flags: ['ride_paid', 'zone'],
  snapshot: { zone: { verdict: 'black', edgeDist: 2, borderline: true }, ride: { amt: 80.25 } },
  intents: { finish: true },
  live: { activeRideCount: 0, activeZone: null, graceEnabled: true },
  history: { trustClaims30d: 0, r14Claims30d: 0 },
});
console.log(result.rule, result.action);
```

Поле `intents` — намерения, распознанные из текста обращения (finish, broken, fineDispute,
balanceOut и т.д.). В файле расхождений (`04`) они уже посчитаны и приложены к каждому случаю,
так что для тестового задания воспроизводить их не нужно.
