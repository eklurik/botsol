## Ітерація 1 — візуалізатор + ПАБЛІШИНГ (локально)

**Мета:** цикл «відкрив сторінку → змінив правило → Опублікувати» працює end-to-end локально,
з тестовим гейтом. Паблішинг = **git-коміт графа у цьому репо** (bikenow-docs, тестовий контур),
БЕЗ push і БЕЗ будь-якого звʼязку з prod-рулами.

**Компоненти:**
1. `editor/server/publish-server.mjs` — локальний node-сервер: віддає `dist/` + API:
   - `GET /api/graphs` — перелік графів (name, file, число кейсів);
   - `GET /api/graphs/:name` — поточний JSON графа;
   - `POST /api/publish/:name` `{graph, label?}` — конвеєр: валідація структури → запис у тимчасову
     копію → прогін ПОВНОГО набору кейсів раннерами → зелено: запис файла + `git commit`
     (тільки файли `prototypes/fines-jdm/`), червоно: відкат + список кейсів, що впали. Без push.
2. Кнопка **«Опублікувати»** на сторінці: показує результат гейта (пройшло/не пройшло, які кейси
   впали, hash коміта).
3. Конвеєр — чисті функції з юніт-тестами (node:test, TDD): `validateGraph`, `runCaseGate`,
   `commitGraph` (тестуються на фікстурному temp-git-репо).

**Локальна перевірка (критерій прийняття):**
- [ ] `npm run serve` (editor/) → сторінка на localhost, графи вантажаться з API — бейдж «джерело: диск (live)»;
  (без сервера сторінка свідомо працює зі вбандленими копіями — read-only fallback для статичної роздачі);
- [ ] змінити суму у драбині (500→501) → Опублікувати → гейт ЧЕРВОНИЙ, показані кейси, файл НЕ змінено;
- [ ] змінити текстову мітку/опис рядка → Опублікувати → гейт зелений, зʼявився коміт, `git show` показує дифф;
- [ ] юніт-тести конвеєра зелені; повний `npm test` прототипу зелений.

## Ітерація 2 — Langfuse локально + РЕАЛЬНІ дані з прода

**Мета:** побачити аналітику рішень правил у Langfuse на реальному тижні/місяці трафіку.
Дані — read-only експорт `solomiya_events` по SSH (той самий канал, що у shadow-реплею).
Стек — повністю локальний (Docker), назовні нічого не шлеться.

**Компоненти:**
1. `prototypes/langfuse-local/docker-compose.yml` — self-host Langfuse v3 (web+worker, postgres,
   clickhouse, redis, minio), версії запінені, headless-провіжининг проєкту і ключів через
   `LANGFUSE_INIT_*` (щоб інгест працював без кліків у UI).
2. `prototypes/langfuse-local/export-events.sh` — SSH-експорт (read-only) подій правил за N днів
   у `data/events.jsonl` (розширення того, що вже робив shadow-реплей).
3. `prototypes/langfuse-local/ingest.mjs` — маппінг подія→трейс: name=правило, timestamp=at,
   metadata (flags, action, executable, executed, arm/phase), tags (rule, active/shadow),
   score `executed`; батчами через `/api/public/ingestion`.
4. `README.md` — як підняти, інгестувати, що дивитись (дашборди: трафік по правилах, частка
   executed, розподіл по днях, деталка трейса з текстом звернення*).
   *тексти клієнтів лишаються НА ЦІЙ машині (локальний стек) і не комітяться — як shadow-*.jsonl.

**Локальна перевірка (критерій прийняття):**
- [ ] `docker compose up -d` → Langfuse UI відкривається, логін працює (init-креденшли);
- [ ] свіжий експорт по SSH за ≥7 днів → `node ingest.mjs` → у UI видно ≥1000 трейсів;
- [ ] розріз по правилах збігається з розподілом shadow-звіту (GR1 найбільший, далі RN2/R13/…);
- [ ] можна відкрити трейс GR1 і побачити метадані рішення (flags, action, executed).

## Межі безпеки (діють на всі ітерації)

1. Прод не читає ці графи; publish = коміт у ТЕСТОВОМУ репо, без push і без деплою.
2. Доступ до прод-БД — тільки read-only SELECT по SSH; жодних write.
3. Вигрузки з текстами клієнтів (`*.jsonl`, `data/`) — у .gitignore, живуть лише локально.
4. Секрети Langfuse — локальні дефолти для localhost, ніде повторно не використовуються.
